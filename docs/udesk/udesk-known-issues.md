# UDesk: ปัญหาที่รอแก้

รายการที่ผู้ใช้แจ้งระหว่างไล่ตรวจโปรแกรม จดไว้ที่นี่แล้วแก้รวมรอบเดียว

## ยังเปิดอยู่

### 6. (สำคัญ) หลังมีคนรีโมทเข้ามา เซสชัน Windows ของผู้ใช้ถูกตัดออกจากจอ และหน้าต่าง UDesk ขึ้น "ไม่พร้อมใช้งาน"

- 2026-11-27 เครื่อง 319080333 (Windows 11 Pro 26300, UDesk 1.0.2) เก็บหลักฐานได้จากเครื่องจริง:
  - 18:48:21 มีการเชื่อมต่อเข้าจากโน้ตบุ๊ก 251147855 (log `cm`)
  - 18:48:37 โปรเซส `--server` เดิมหายไป บริการสร้างตัวใหม่ (PID 175200) ใน **session 2**
  - `qwinsta`: session 1 (ผู้ใช้) สถานะ `Disc`, `console` เป็น session 2 ไม่มีผู้ใช้ = จออยู่ที่หน้าล็อกอิน Windows
  - หน้าต่างหลักและ tray ใน session 1 ขึ้น `ipc connection closed: reset by the peer` ทุกวินาที
    เพราะ IPC ของ `--server` รับเฉพาะ session เดียวกัน (`src/ipc/auth.rs` expected_session_id)
  - ผลที่ผู้ใช้เห็น: แถบแดง "ไม่พร้อมใช้งาน" และรหัสผ่านครั้งเดียวบนจอเป็นค่าค้าง ใช้ไม่ได้
- สาเหตุที่น่าจะใช่ (ผู้ใช้แจ้งว่าเข้าเครื่องจากบ้านผ่าน Tailscale ซึ่งใช้ Remote Desktop ของ Windows):
  การล็อกอิน RDP ยึด session 1 ไป จอจริงจึงเกิด session 2 ที่หน้าล็อกอิน และบริการ UDesk ไปให้บริการ session 2
  ไม่ใช่ UDesk ตัดเซสชันเอง หลัง 18:56 ผู้ใช้เปิด UDesk ใหม่ใน session 1 ได้ ขณะที่ LogonUI และ `--server` ยังอยู่ session 2
- สิ่งที่ควรแก้ในโปรแกรม:
  1. เมื่อ IPC ถูกปฏิเสธเพราะคนละ session ให้ขึ้นข้อความ "เครื่องนี้กำลังถูกใช้ผ่าน Remote Desktop" แทน "ตรวจสอบอินเทอร์เน็ต"
     และไม่แสดงรหัสผ่านค่าค้าง
  2. ตรวจว่าทำไม `share_rdp` (ค่าเริ่มต้นเปิด, `src/platform/windows.rs`) ไม่พา `--server` ไป session ของ RDP
- น่าจะเป็นสาเหตุเดียวกับข้อ 1 (อาการเดียวกัน: ไม่พร้อมใช้งาน + รหัสผ่านไม่อัปเดต)
- ยังไม่รู้: อะไรทำให้ session 1 ถูกตัดออกจาก console หลังการเชื่อมต่อเข้า 16 วินาที
  (ปุ่มล็อก/สลับผู้ใช้จากฝั่งควบคุม? จอเสมือน amyuni? พฤติกรรมของ Windows build นี้?)
- ต้องตรวจ: log ของ `--server` ใน profile ของ SYSTEM (ต้องสิทธิ์ผู้ดูแล), ทำซ้ำโดยรีโมทเข้าแล้วดู `qwinsta`
- ผลกระทบ: ถ้าไม่ได้ตั้งรหัสผ่านถาวร จะรีโมทกลับเข้าเครื่องไม่ได้ เพราะรหัสครั้งเดียวตัวจริงไม่แสดงที่ไหน

### 1. เปิดโปรแกรมแล้วค้างที่ "ไม่พร้อมใช้งาน" ต้องปิดแล้วเปิดใหม่

- พบเมื่อ: 2026-11-27, Windows, UDesk 1.0.0, เครื่องอยู่นอกวงแลน
- อาการ: แถบสถานะขึ้นสีแดง "ไม่พร้อมใช้งาน กรุณาตรวจสอบการเชื่อมต่ออินเทอร์เน็ตของคุณ"
  ช่องรหัสผ่านครั้งเดียวค้างที่ "กำลังสร้าง…" และลายนิ้วมือในหน้าเกี่ยวกับว่าง
  ออกจากโปรแกรมแล้วเปิดใหม่จึงขึ้น "พร้อม"
- สิ่งที่ยืนยันแล้ว:
  - ไม่ใช่ปัญหาเซิร์ฟเวอร์: ใน log ของ hbbs เครื่องนั้นลงทะเบียนจาก IP ภายนอกได้หลังเปิดใหม่
    และพอร์ต TCP 21115–21117 เปิดจากภายนอก
  - รหัสผ่านค้าง "กำลังสร้าง…" แปลว่าหน้าต่างหลักต่อ IPC กับโปรเซส `--server` ไม่ได้เลย
  - โค้ดฝั่ง Rust (`check_connect_status_` ใน `src/ui_interface.rs`) วนต่อ IPC ใหม่เองอยู่แล้ว
    ดังนั้นสาเหตุไม่ใช่ "หน้าต่างไม่ลองใหม่" น่าจะเป็นโปรเซส `--server` ไม่ได้ทำงานอยู่ตอนนั้น
- ยังไม่รู้: ทำไมโปรเซส `--server` ไม่ทำงาน (หลังติดตั้งทับ? หลังย้ายเครือข่าย?) และพอร์ต UDP 21116
  จากภายนอกยังไม่ได้ทดสอบ
- ต้องการเพื่อไปต่อ: log จากเครื่องที่เป็นตอนเกิดอาการ ที่ `%APPDATA%\UDesk\log` และ
  `C:\Windows\ServiceProfiles\LocalService\AppData\Roaming\UDesk\log` ยังไม่ได้แก้โค้ดเพราะยังไม่รู้สาเหตุ

### 2. ระบบอัปเดตในโปรแกรม: รอผู้ใช้กดทดสอบจริง

- 1.0.1 ออกแล้ว เครื่องที่ลง 1.0.0 ตัวที่มีระบบอัปเดต (build ตั้งแต่ 17:25 ของ 2026-11-27) ควรเห็นแถบสีส้ม
- ยังไม่ได้พิสูจน์: แถบขึ้นจริง, กด "อัปเดต" แล้วโหลด ตรวจ SHA-256 และเปิดหน้าติดตั้งได้,
  ติดตั้งทับขณะโปรแกรมเปิดอยู่แล้วกลับมาใช้งานได้
- ยังไม่มีบน macOS

### 3. ภาพเดสก์ท็อปบนการ์ดเครื่อง: รอทดสอบกับการรีโมทจริง

- ทำแล้วใน 1.0.1 (`flutter/lib/udesk/udesk_thumb.dart`) แต่ยังไม่ได้เห็นทำงานจริง
- ต้องดู: ภาพขึ้นบนการ์ดหลังรีโมท, ไม่มีหน้าต่าง "บันทึก/คัดลอก screenshot" เด้งขึ้นเอง,
  ฝั่งถูกควบคุมไม่ต้องกดอนุญาตเพิ่ม, เครื่องปลายทางหลายจอ

### 5. "การเชื่อมต่อไปยังเซิร์ฟเวอร์ Relay ล้มเหลว" จากนอกวงแลนเข้าเครื่องในวงแลน (เป็นบางครั้ง)

- 2026-11-27 18:49: โน้ตบุ๊ก 251147855 (นอกวงแลน) → 319080333 (ในวงแลนเดียวกับ NAS)
- log ของ hbbr: 18:48:39 และ 18:49:08 จับคู่ relay สำเร็จ (แต่ละครั้งปิดหลัง ~20 วินาที)
  18:49:31 มีคำขอ relay จากฝั่งเครื่องในวงแลน (192.168.1.254) แต่ฝั่งโน้ตบุ๊กไม่เข้ามาจับคู่
- พอร์ต TCP 21115–21117 เปิดจากภายนอกและจากในวงแลน ณ เวลาตรวจ
- ข้อสังเกต: hbbs เห็นเครื่องในวงแลนเป็น IP ของเราเตอร์ (192.168.1.254, hairpin NAT)
  การเชื่อมต่อนอก↔ในจึงต้องผ่าน relay เสมอ ต่อตรงไม่ได้
- ยังไม่รู้: ทำไมฝั่งนอกต่อ relay ไม่ถึงในครั้งที่สาม (เครือข่ายฝั่งโน้ตบุ๊ก? เราเตอร์/NAS จำกัดการเชื่อมต่อถี่ ๆ?)
- ขั้นต่อไปถ้าเกิดซ้ำ: เก็บ log ฝั่งโน้ตบุ๊ก `%APPDATA%\UDesk\log`, ตรวจ auto-block/DoS protection ของ NAS และเราเตอร์

### 4. (ข้อเสนอ รอผู้ใช้ยืนยัน) กันการเชื่อมต่อเข้า ID ของเครื่องตัวเอง

# UDesk — ระบบแอดมินสูงสุด (super-admin) — เอกสารออกแบบ (ร่าง)

สถานะ: ร่าง รอผลสำรวจ flow auth ก่อนเติมส่วนเทคนิคการเชื่อมต่อ ยังไม่เริ่มเขียนโค้ด

## เป้าหมาย

ให้เจ้าของงาน (แอดมินสูงสุดคนเดียว) ดูแลและรีโมทเข้าเครื่องที่ติดตั้ง UDesk ได้จากที่เดียว
อย่างปลอดภัย โดยไม่ต้องมีรหัสผ่านฝังในตัวติดตั้ง และไม่ต้องไปตั้งค่าทีละเครื่อง

## สิ่งที่เจ้าของงานเลือก/กำชับ (2026-11-28)

1. **ไม่มีตัวติดตั้งแอดมินแยกสำหรับเครื่องสำนักงาน** — ทุกเครื่องใช้ตัวปกติ (จะเอาตัวติดตั้ง admin เดิมออก)
2. **กลไกความปลอดภัย = กุญแจสาธารณะ** (public-key) — ปลอดภัยสุด ไม่มีความลับหลุดจากตัวติดตั้ง
3. **ตัวแอดมินของเจ้าของงานหน้าตาต่าง** (เช่น สีโปรแกรมต่าง) เพื่อให้รู้ว่าอยู่ในโหมดแอดมิน
   — ใช้กับเครื่องตัวคุมของแอดมินเท่านั้น เครื่องสำนักงานยังเป็นตัวปกติ
4. **แผงแอดมินแสดงเครื่องทั้งหมดที่ติดตั้งโปรแกรม** พร้อมภาพหน้าจอ (ภาพย่อ + ออนไลน์ กดเข้าดูสดได้)
5. **ยืนยันตัว 2 ชั้นก่อนเข้าเครื่อง** — ชั้นแรกล็อกอิน Google (บัญชีแอดมิน), ชั้นสอง OTP (อีเมล หรือยืนยันซ้ำ)

## องค์ประกอบ

### 1. กุญแจแอดมิน (public-key)

- สร้างคู่กุญแจ ed25519 ครั้งเดียว: private key อยู่กับแอดมินที่เดียว (ไฟล์ secrets เครื่องแอดมิน ไม่ขึ้น git)
- public key ฝังในโค้ด/คอนฟิกของตัวปกติทุกเครื่อง (เปิดเผยได้ ไม่เป็นความลับ)
- เปลี่ยนกุญแจ = ออกรุ่นใหม่ที่ฝัง public key ใหม่

### 2. แผงแอดมินสูงสุด (admin dashboard)

- เปิดได้เฉพาะเมื่อ: ล็อกอิน Google เป็นบัญชีแอดมิน (UID ตรงกับที่กำหนด) — gate ที่ฝั่ง UI + Firestore rules
- ดึงรายชื่อเครื่องที่เคย/กำลังออนไลน์จาก Firestore (ระบบ log เดิม `udesk_log` มี device ID, เวลา, เวอร์ชัน)
  อาจต้องเพิ่ม heartbeat/online-status ให้แม่นขึ้น
- แสดงภาพย่อหน้าจอ (ใช้ `UdeskThumb` ที่ทำไว้) + สถานะ กดเข้าเพื่อรีโมทสด
- หน้าตาต่าง (ธีมสี/ป้ายกำกับ "แอดมินสูงสุด")

### 3. การยืนยัน 2 ชั้นก่อนเชื่อมต่อ

- ชั้น 1: ล็อกอิน Google = บัญชีแอดมิน (มีอยู่แล้วบางส่วน)
- ชั้น 2 (เลือกหนึ่ง — ใส่ให้เทียบในดีไซน์):
  - **OTP อีเมล**: ต้องมี Firebase Cloud Function ส่งอีเมล (เพิ่ม infra เล็ก ๆ) เก็บ OTP ชั่วคราวใน Firestore
  - **ยืนยันซ้ำ Google (reauth)**: ใช้การยืนยันตัวซ้ำของ Google ไม่ต้องมี backend ส่งเมลเอง แต่พึ่ง 2FA ของบัญชี Google
- ผ่านชั้น 2 แล้วจึงอนุญาตให้เซ็น challenge เพื่อเข้าเครื่อง

### 4. จุดเชื่อม auth ของการเชื่อมต่อ (สำรวจแล้ว — จุดเชื่อมชัดเจน)

**ข่าวดี:** protobuf ที่ต้องแก้ (`LoginRequest`, `Hash`) อยู่ใน `libs/base/protos/message.proto` = crate `base`
ไม่ใช่ submodule `hbb_common` ที่แพง แก้แล้ว regen ตอน build ได้เลย และเข้ากันได้กับเวอร์ชันเก่า (ฟิลด์ใหม่ถูกเมิน)

crypto ที่มีอยู่แล้วให้ reuse: `hbb_common::sodiumoxide::crypto::sign` (ed25519) — เซิร์ฟเวอร์เซ็น identity ตัวเองด้วยตัวนี้อยู่แล้ว
ฝั่งตรวจใช้ `sign::verify_detached`

**กลไก (challenge–response):**
1. ฝังค่าคงที่ `UDESK_ADMIN_PUB_KEY` (ed25519 public key ของแอดมิน) ในตัวปกติทุกเครื่อง (เปิดเผยได้) private key อยู่กับแอดมิน
2. เพิ่มฟิลด์ใน `Hash` (ส่งไปหา client ตอนเปิดการเชื่อมต่อ): `bytes admin_challenge` = สุ่ม 32 ไบต์ต่อการเชื่อมต่อ
   (ของเดิม `hash.challenge` ยาวแค่ 6 ตัว สั้นไปสำหรับลายเซ็น จึงเพิ่มฟิลด์ใหม่) — `connection.rs:551-556`
3. เพิ่มฟิลด์ใน `LoginRequest`: `bytes admin_signature`
4. ฝั่งแอดมิน (ตัวคุม) เซ็น `admin_challenge || target_device_id` ด้วย private key ใส่ใน `admin_signature`
   (ผูก device id กันเอาลายเซ็นของเครื่องหนึ่งไปใช้กับอีกเครื่อง)
5. เครื่องปลายทางตรวจที่จุดตัดสิน auth (`connection.rs:3102-3155`): ถ้า `admin_signature` ผ่าน
   `verify_detached(sig, admin_challenge||my_id, UDESK_ADMIN_PUB_KEY)` → ถือว่าเป็นแอดมิน → auto-accept เงียบ
   (ข้ามรหัสผ่าน, set authorized=true, ซ่อน CM) และยังบันทึก log — ก่อน/คู่กับ path ตรวจรหัสผ่านเดิม

**จุดแก้โค้ด (จากผลสำรวจ):**
- `libs/base/protos/message.proto`: เพิ่ม `Hash.admin_challenge`, `LoginRequest.admin_signature` (regen ตอน build)
- `src/server/connection.rs`: สร้าง `admin_challenge` ตอน `start` (~551), ตรวจลายเซ็นในบล็อก auth (~3102-3155)
- `src/client.rs` / จุดสร้าง LoginRequest: ถ้าโหมดแอดมินและมี private key → เซ็นแล้วแนบ
- ค่าคงที่ `UDESK_ADMIN_PUB_KEY` (เช่นใน `libs/base` หรือโมดูล udesk)

**ความเข้ากันได้:** เครื่องที่ไม่มีฟิลด์ใหม่ (รุ่นเก่า) ยังทำงานปกติ (proto3 เมินฟิลด์ที่ไม่รู้จัก)
ช่องทางรหัสผ่านเดิมยังอยู่ครบ ไม่ถูกแตะ

## Threat model / จุดที่ต้องระวัง

- private key ของแอดมินหลุด = เข้าได้ทุกเครื่อง → ต้องเก็บดีมาก, มี 2FA เป็นชั้นกันพลาด, รองรับการ revoke (ออกรุ่นใหม่)
- public key ในตัวติดตั้งแกะได้ แต่ไม่เป็นความลับ (ยืนยันลายเซ็นเท่านั้น ปลอมไม่ได้ถ้าไม่มี private key)
- ต้องกัน replay: challenge ต้องสุ่มใหม่ทุกครั้ง มีอายุสั้น ผูกกับ session/เครื่องปลายทาง
- ยังบันทึกทุกการเข้าถึงใน Firebase เพื่อ accountability
- ความรับผิดชอบองค์กร: แจ้งพนักงานตามนโยบายการเฝ้าดูที่ทำงาน (เรื่ององค์กร ไม่ใช่ตัวโปรแกรม)
- **กันประตูหลังในตัวแจกสาธารณะ (สำคัญ, 2026-11-28):** public key ถูก gate ด้วย env `UDESK_ADMIN_PUB_KEY`
  ตอน cargo build (`libs/base/src/lib.rs` ใช้ `option_env!`) build ที่ไม่ตั้ง env จะไม่มี public key และ
  `verify_admin_signature` คืน false เสมอ = **ไม่รับแอดมินเลย** ดังนั้น build ที่แจกคนทั่วไป (เว็บ) ต้องไม่ตั้ง env นี้
  มีแต่ build สำหรับเครื่องสำนักงานที่เจ้าของงานเป็นเจ้าของเท่านั้นที่ตั้ง env → เครื่องคนนอกถูกเข้าเงียบไม่ได้

## สิ่งที่จะเลิกใช้

- ตัวติดตั้ง admin แบบรหัสฝัง (`UDESK_ADMIN` build + `UDesk-Admin-*.exe`) — แทนที่ด้วยระบบนี้
  (ยังไม่ลบโค้ดจนกว่าระบบใหม่จะพร้อม)

## การตัดสินใจ (2026-11-28)

- **ชั้น 2 = OTP อีเมล** ผ่าน Cloudflare Worker + email API (เช่น Resend free tier) เก็บ OTP ชั่วคราวใน Firestore
  (SMS ทำได้แต่เสียเงินต่อข้อความ เลือกอีเมลก่อน)
- **แผงแอดมิน = ภาพหน้าจอล่าสุด (ไม่ใช่วิดีโอสด)** — แก้ความเข้าใจ 2026-11-28: เครื่องที่ออนไลน์แสดง
  ภาพหน้าจอล่าสุด เครื่องออฟไลน์จอดำ ไม่ต้องสตรีมสดหลายเครื่อง (เบากว่ามาก ใกล้กับ `UdeskThumb` ที่ทำไว้)
  กดเครื่องไหนค่อยเข้ารีโมทสดเครื่องเดียว
  - **สรุป 2026-11-28:** ใช้ `UdeskThumb` ที่ทำไว้ — ภาพย่อเก็บในเครื่องแอดมินจากครั้งที่รีโมทเข้าไป
    ไม่อัปโหลดขึ้นคลาวด์ เครื่องที่ยังไม่เคยเข้าก็จอดำ (ความเป็นส่วนตัวสูงสุด)

## ลำดับงาน (4 ขั้น เก็บช่องทางเดิมไว้ครบทุกขั้น)

1. **แกน auth กุญแจสาธารณะ (Rust + proto)** — สร้างคู่กุญแจแอดมิน, ฝัง public key, เพิ่มฟิลด์ proto,
   ตรวจลายเซ็นแล้วรับเงียบ; ทดสอบว่า admin-signed เข้าได้เงียบ และรหัสผ่านเดิมยังทำงาน
2. **แผงแอดมินสูงสุด (Dart)** — UI หน้าตาต่าง (ธีมแอดมิน), gate ด้วยบัญชี Google แอดมิน,
   ดึงเครื่องออนไลน์จาก Firestore, ฝั่งตัวคุมเซ็น challenge เข้าเครื่อง
3. **2FA (Cloudflare Worker + OTP อีเมล) — เก็บกุญแจฝั่งเซิร์ฟเวอร์ (ตัดสิน 2026-11-28)**
   - **ไม่ฝังกุญแจส่วนตัวในไบนารีตัวแอดมินอีกต่อไป** (เลิกใช้ option_env UDESK_ADMIN_KEY)
     กุญแจส่วนตัวเก็บใน Cloudflare (KV/secret) ปล่อยให้ตัวแอดมินหลังผ่าน Google login + OTP เท่านั้น
   - Worker: `POST /request-otp` {idToken} → ตรวจ Firebase JWT ว่าเป็น UID แอดมิน → สุ่ม OTP เก็บใน KV (อายุสั้น)
     ส่งอีเมลผ่าน Resend; `POST /verify-otp` {idToken, otp} → ตรวจ OTP → คืนกุญแจส่วนตัว (ครั้งนั้น ถือใน RAM)
   - แอป: ตัวแอดมันล็อกอิน Google → ขอ OTP → กรอก → ได้กุญแจ → ตั้งกุญแจใน Rust ผ่าน FFI (ไม่บันทึกลงดิสก์)
     ไม่ผ่าน 2FA = ไม่มีกุญแจ = เซ็นไม่ได้
   - Rust: `udesk_admin_sign` อ่านกุญแจจาก global ใน RAM ที่ Dart ตั้งให้ (แทน option_env)
   - ต้องใช้จากเจ้าของงาน: บัญชี Cloudflare (Worker + KV), Resend API key + อีเมลผู้ส่งที่ยืนยันแล้ว, อีเมลแอดมินรับ OTP
4. **กริดภาพหน้าจอล่าสุด + สถานะออนไลน์** (ไม่ใช่วิดีโอสด) — ต่อยอด `UdeskThumb`, กดเข้ารีโมทสดทีละเครื่อง
